# 2026-11-18 前后端全量联调与 Podman 基线方案（FE-029 / BE-043）
## 普通图片上传契约补充（R3 `APPROVE`）

真实 Chromium 在 JWKS 同步后提交 `POST /api/v1/files/generic` 返回 HTTP 400、`code=400`。前端普通与增强组件、API 封装使用 `sex=0/1`，后端 `FileHandler` 要求 `1=AM`、`2=AF`。保留组件和调用方的 `0=AM`、`1=AF`，只在构造普通上传表单时统一映射到 `1/2`；不修改后端校验、分片协议、已有组件调用方或认证。回归覆盖两种取值、两个组件的 Element Plus 直传及增强组件裁剪和粘贴共用的 XHR 表单，并在隔离栈复验浏览器选图与结果渲染。

## 背景

前端 `apex-admin-web` 与后端 `apex-scaffold` 已有真实联调历史：FE-026 记录了经网关验证 18 条接口 18/18，并修复办公列表、日期、用户状态等契约问题。该记录并不覆盖所有前端 API、页面写操作、分页/错误语义及当前容器网络配置。后端已有 `podman-compose.yml` 和可选前端服务；本任务将后端 Compose 作为唯一容器编排入口，前端仅独立构建镜像并接入该服务。

## 目标

- 建立唯一、可重复的 Podman Compose 联调环境：以 `apex-scaffold/podman-compose.yml` 作为全栈唯一编排入口；前端镜像独立预构建，由后端 Compose 的 `apex-admin-web` 服务接入同一网络访问网关。
- 以执行代码与 `docs/03-api/API_ROUTES.md` 为后端路由基线，逐项映射全部前端 `src/api/` 导出函数的路径、方法、参数、响应包装、分页及权限/租户要求；标注页面是否实际消费。静态映射覆盖不等同于所有接口均已真实运行验证。
- 通过真实容器链路验证登录/刷新、身份与菜单、工作台聚合、主要业务域列表、关键读写路径及 SSE/WebSocket（在依赖和凭据可用时）；只把实际取得的状态码和响应数据计为证据。
- 修复联调中确认的前端/后端缺陷，补回归测试，并同步 API 契约说明、部署与联调文档、Compose/脚本、测试代码及分层测试报告。
- 未具备第三方凭据、业务测试数据或环境能力的链路必须标记为未验证，不得以 mock 或历史测试替代真实端到端证据。

## 影响面

- 前端：`src/api/**`、涉及页面与 Vitest/E2E；移除重复的前端 Compose 文件；使用 `Containerfile` 与 `podman build` 构建镜像，由后端 `podman-compose.yml` 统一编排，并同步文档与联调报告。
- 后端：`podman-compose.yml`、必要的服务配置/路由/DTO/处理器及测试；仅在真实联调定位到缺陷后按最小范围修改。数据库迁移和共享 DTO 需单独列明并先由 R3 评审。
- 证据：生成 API 对照矩阵和真实 HTTP 冒烟记录，分别登记在两仓的测试报告与改造记录中；任务状态与记忆台账由 R0 维护。

## 兼容性

- 不升级或替换既有技术栈，不改变对外接口语义来迁就单侧实现；确需调整契约时，前后端同步修改、补兼容性说明和测试。
- 开发环境仍允许 `npm run dev` 通过 Vite 代理访问宿主网关；本任务要求的可复现验收环境统一为 Podman Compose。

- 不提交凭据、令牌、生产数据或本地环境文件；测试数据必须可标识、可清理且限定本地环境。

## 菜单初始化失败降级

- FE-029 独立 R3 方案评审通过（`menu_plan_review`）。原守卫在菜单加载失败时将已可解析的静态目标重定向到自身，把单次失败放大为连续请求。
- 仅在动态路由注册完成、且当前目标由 NotFound 重新解析为实际路由时执行同址替换，并保留 query/hash。菜单初始化失败时放行本次导航、保留静态路由；下一次导航可重试。注册完成后才更新响应式侧栏数据与成功标记，已注册的动态记录在注册失败时撤销。不改 API、权限检查或会话清理规则。
- 验收：首个菜单请求返回 503 时，登录仍能进入静态工作台，菜单只请求一次；后续主动导航在菜单恢复后可进入动态页面，侧栏同步更新。保留正常点击与刷新直达覆盖，直达地址完整保留 query/hash。

## 字典接口 ID 精度待确认

- 在隔离环境中对齐网关与 system 的精确 CORS 来源后，字典创建 HTTP 200、`code=0`，页面可见新记录，但编辑 HTTP 500、`code=4711`。字典持久层使用 `ASSIGN_ID`，字典类型与数据 DTO 当前对外输出 Java `Long` 数字，浏览器可能在解析时丢失精度。
- 先对比字典列表响应中原始 ID 与浏览器提交的路径 ID，只输出是否一致，不输出原始 ID。若确认精度问题，建议沿用系统用户 DTO 的做法：仅对字典类型和数据响应 ID 使用十进制字符串，保留请求路径和数据库字段类型；前端接受字符串及历史安全整数，不对字符串做数字转换。
- 独立 R3 通过后才修改接口；回归覆盖大于 `Number.MAX_SAFE_INTEGER` 的 ID 在列表、修改、启停与删除中原样传递，再执行真实字典页面 CRUD。
- 真实续测确认类型和数据项可创建、编辑；数据项停用返回 `code=0` 后，管理列表只查启用项，导致无法再次启用。该仓储查询仅服务现有管理列表；去掉此查询的启用状态过滤，保留类型过滤、排序、逻辑删除与权限不变。浏览器回归要求停用后仍可见、可重新启用，再验证删除。

- Compose/脚本/文档按文件回滚；业务代码与契约修复按独立提交回滚，数据库变更如确有必要必须提供前向兼容和回滚步骤并单独评审。
- 不清理现存 Podman 容器、卷或用户数据；执行前记录容器/网络状态，测试后只清理本任务创建且可确认归属的临时测试数据。
- 采用 `git revert` 回滚已提交改动；不使用 `reset --hard` 或覆盖他人工作区。

## 验收标准

1. R3 独立评审方案通过后再进入执行；任务卡具备 R0、基线、互斥写入范围、具体独立复核者及验收命令。
2. 后端 `.env` 从 `.env.example` 准备且必填本地密钥非空；显式指定 `-p apex-scaffold`；`podman-compose -p apex-scaffold -f podman-compose.yml config` 通过。所需后端服务和前端容器健康；前端容器能解析 `apex-gateway` 并成功反代.
3. API 对照矩阵静态映射覆盖全部前端 API 导出函数，列明路由、请求/响应/分页/鉴权差异及验证状态；静态映射不等同于全部接口真实 E2E。

5. 前端 `npx vue-tsc --noEmit`、`npx vitest run`、`npm run build`、`npm run test:e2e` 和治理检查通过；后端按固定 JDK/mvnd 对受影响模块的定向测试、格式和治理检查通过。
6. 两仓分别更新契约文档、Podman 指南/配置、测试代码及测试报告；记录所有真实请求方法、路径、状态、必要的脱敏响应摘要、环境基线、未验证边界和清理证据。
7. 指定的 R5 `integration_final_reviewer` 必须与执行者为不同独立上下文；复核绑定最终待复核 SHA。R5 通过、集成和全部留痕完成后才允许关闭任务。
