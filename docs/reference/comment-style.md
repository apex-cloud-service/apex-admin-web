# 注释规范

> 依据 2026-10-06《注释现状报告》对全仓库 105 个 TS/Vue 源文件的扫描结果制定，并经评审确认。规范向存量正确风格靠拢，不要求重写既有注释。

## 1. 注释语言：中文（技术名词保留英文）

- 说明文字、原因、约束用中文；标识符、类型名、HTTP 方法、接口路径、权限码、第三方术语（PKCE、JSDoc、ECharts 等）保留英文原样，不翻译。
- 禁止中英混排的同义重复（如 `// token 令牌`）。
- 与 AGENTS.md 的关系：AGENTS.md「除明确要求外，不新增代码注释」的克制原则优先，本规范约束「需要写注释时怎么写」。

## 2. 文件头模板（按需参考）

### 2.1 `.ts` 文件（JSDoc，置于第 1 行）

```ts
/**
 * <模块名>：一句话职责（名词短语）
 * ------------------------------------------------------------------
 * 用途：
 * <这个文件为什么存在、被谁使用、不负责什么。2~4 行。>
 *
 * 覆盖：<可选：功能域枚举，只列已实现的>
 *
 * @author <姓名或团队名>
 * @date YYYY-MM-DD
 */
```

### 2.2 `.vue` 文件（HTML 注释，置于文件第 1 行、`<template>` 之前）

```html
<!--
  <页面/组件名>
  ------------------------------------------------------------------
  用途：<职责，1~3 行>

  功能：
  - <只列实际已实现的能力，逐条可与代码对上>

  权限要求：<页面含 v-permission 按钮时必填，必须与代码实际值一致>
-->
```

### 2.3 测试文件（简化式）

```ts
/**
 * <被测对象> 单元测试
 * ------------------------------------------------------------------
 * 覆盖：<测试场景类别>
 */
```

### 2.4 字段规则

| 字段 | 要求 | 维护规则 |
| --- | --- | --- |
| 职责/用途 | 必填 | 修改文件职责时必须同步 |
| `@author` / `@date` | 新建文件必填 | 反映创建时刻，写入后永不更新；修改历史由 git 记录，头注不追写「修改记录」段 |
| 功能清单 | 有则必真 | 每条必须能在代码中找到对应实现；禁止写入规划中、未实现的能力 |
| 端点/权限码清单 | 新建 `.ts` 文件不在头注罗列 | 见 2.5 |

### 2.5 头注中「易漂移清单」的处理

头注罗列端点/权限码清单是注释过时的主要来源（制定本规范时的实例：`auth-config.ts`、`oauth2/callback.vue`、`office/approval/index.vue`）。

- **新建文件**：如接口路径对调用者有帮助，可写在 API 函数自己的 JSDoc 首行（如 `/** 获取用户列表。GET /admin-api/v1/users */`），头注只写稳定的职责概述。
- **存量文件**：现有清单保留；文件发生接口变更时应核对相关注释与实现是否一致，但不要求为本次变更之外的存量文件补写注释。

## 3. 类 / 函数 / 方法文档模板

### 3.1 完整式（适用于需要补充契约说明的导出函数、类、composable 或 API 函数）

```ts
/**
 * <动词开头的动作说明，句末句号>。
 *
 * <补充约束：调用时机、幂等性、失败语义等；没有就省略>
 *
 * @param params 查询参数（<必填/可选、格式、枚举含义>）
 * @returns <返回内容、结构、单位；分页须写明 list/total>
 * @throws ApiError <确实会抛出的业务错误>
 * @example
 * ```ts
 * const res = await listUsers({ page: 1, size: 20 })
 * ```
 */
```

- 使用 `@param` 或 `@returns` 时，参数顺序应与签名一致；可选参数标注「可选」。
- 需要返回值说明时统一用 `@returns`（与存量一致，不用 `@return`）。
- `@throws`、`@example` 为条件段：确实抛错/用法不直观才写，禁止为凑字段编造。
- 类型来源能引用 DTO 名就引用，不复述字段结构。

### 3.2 简式（`.vue` 内部业务函数、非导出工具函数）

```ts
/** 加载当月全部事件到本地缓存 */
const loadAllEvents = async () => {
```

- 一行说清「做什么 + 关键语义」，不超过一行。
- 琐碎函数（纯事件转发、简单格式化）允许不写，不以注释凑数。

### 3.3 类型与字段

- 字段注释在字段语义不自明、存在枚举约束或需要说明单位时使用单行 `/** */`；枚举值可用 `A=1 含义 B=2 含义` 紧凑写法。
- 与后端 DTO 对应且确需补充说明的类型，可写明「对应后端 DTO 名」。

## 4. 行内注释规则

**何时写（只允许这四类）：**

1. 原因与约束：代码读不出来的「为什么」——魔数来源、绕过缺陷的原因、与后端的隐式契约。
2. 单位与语义：秒/毫秒、字节、枚举含义（如 `ttl = 7 * 24 * 60 * 60 * 1000 // 7天`）。
3. 分节标记：统一 `// ===== 名称 =====`（script）与 `<!-- ========== 名称 ========== -->`（template）；存量其他分隔风格不强制改。
4. 警示：坑与顺序依赖。

**何时不写：** 代码已自明的复述；历史过程（git 负责记录）；为坏味道辩解却无改进路径的注释。

**怎么写：**

- `.ts` 与 `<script>` 内用 `//`；`<template>` 内用 `<!-- -->`；不混用 `/* */` 单行风格。
- 置顶独立行优先；行尾注释仅用于短标注（≤ 30 个汉字）且原行不因此超过约 120 列。
- 独立行注释 ≤ 80 字；超过拆为多行；连续超过 3 行的内容应升级为 JSDoc 或写入 docs/。

## 5. 禁止的坏注释（实例为制定本规范时采集，均已修复）

| # | 类型 | 反例 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 复述代码 | `// 加一` 之于 `count++` | 不写，代码自明 |
| 2 | 与代码不符/过时 | 头注 `POST /api/v1/oauth2/callback`，实现是 `/oauth2/token` | 修注释；接口变更时同步 |
| 3 | 错位 | 「axios 实例」的注释挂在 `refreshPromise` 上 | 注释紧贴被描述符号 |
| 4 | 变更日志式 | 「TypeScript 修复版 / 修复内容：…」 | 头注只写职责；修复历史归 git |
| 5 | 声称未实现 | 头注列「会议室预订」，代码中无此功能 | 只写已实现；规划放 docs/ 或 issue |
| 6 | 头注与代码各说各话 | 头注 `office:approval:create`，按钮 `office:approval:initiate` | 以代码为准修正；权限码以 v-permission 实际值为准 |
| 7 | 注释掉的代码 | — | 直接删除，git 可找回 |
| 8 | 裸 TODO/FIXME | `// TODO 待优化` | 原则上不写；确需保留须含负责人与日期 |
| 9 | 情绪化/无信息 | 「这玩意真坑」「临时处理」 | 写明具体原因与影响范围 |
| 10 | 概括性空话 | 「处理数据」「工具类」 | 写具体：处理什么、给谁用 |

## 6. 与存量注释的兼容性

- 保留不动的存量习惯：`.ts` JSDoc 头注 + 66 连字符分隔线三段式；`.vue` 顶部 HTML 头注；`@returns` 标签；字段单行 JSDoc；template 分节注释。
- **检查注意**：`.vue` 头注是 `<template>` 之前的 HTML 注释，任何自动检查须同时识别该形式，只看 `<script>` 块内部会误报约 13 个文件缺失头注。
- 已有头注的文件不回填 `@author`/`@date`，不因新模板重写。
- 修改任何存量文件时，顺带核对该文件注释与代码的一致性；不做与本次改动无关的注释清扫。
