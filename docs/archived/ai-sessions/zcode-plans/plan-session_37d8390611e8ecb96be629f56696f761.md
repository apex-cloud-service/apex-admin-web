## Context

本轮基于 `/Users/work/apex-scaffold` 当前源码，重新审计了上一轮暂缓的后端能力。结论是：部分能力并非“前端尚未接入”，而是后端实现存在会导致 400/假成功/跨租户风险/数据重复或功能永远无事件的缺陷，需要先修后端契约与运行链路。

已确认的主要问题：

1. **分片上传**核心闭环存在，但 Handler 在响应式链外直接 `Long.valueOf/Integer.valueOf/parseLong`，非法参数会绕过统一错误边界；merge 忽略请求中的 `fileName/contentType/md5`，分片 MD5 与整文件 MD5 只存不校验；上传整片一次读入内存且未按初始化 chunkSize 限制；`file_chunk(file_id, chunk_index)` 没有唯一约束，并发重复上传会留下重复对象/元数据。
2. **文件分享**只有创建/撤销/兑换/下载，没有认证列表端点。直接返回所有分享会造成越权，列表必须按租户、文件归属和当前用户过滤，且不得返回 token/tokenHash。
3. **Keycloak 管理**的 status 是硬编码 connected；单用户同步没有先按 `keycloak_sub` 查询，重复同步会撞唯一键；全量同步吞掉失败后仍返回成功；同步调用配额校验依赖 ThreadLocal `TenantContext`，当前 JWT/Reactive Context 没有稳定桥接；三个 admin 端点没有细粒度 `@RequirePermission`，只有粗粒度 admin role。
4. **通知 SSE**认证和租户隔离已有，但 `apex-notification-topic` 没有任何业务生产者，SSE 只能心跳；payload 是裸字符串、没有 id/retry/schema，且缺少 producer-consumer contract 测试。
5. **认证中心** `/auth/v1/sessions|roles|permissions` 已真实实现，但部分 GET 查询缺少管理员/资源权限门禁；session GET/DELETE 对同一路径使用两种 ID 语义；部分 AuthConfig 端点直接信任 query `tenantId`；system 兼容实现与 auth-service DTO/HTTP 方法重复漂移。

## Recommended implementation

### Phase 1：先修数据安全与输入边界

#### 1. 分片上传修复

修改：

- `apex-file-service/.../interfaces/handler/ChunkHandler.java`
- `apex-file/.../application/service/ChunkUploadService.java`
- `apex-file/.../application/dto/ChunkMergeRequest.java`
- `apex-file/.../infrastructure/.../FileChunkRepositoryImpl.java`
- `apex-file-service/src/main/resources/application.yml`
- 新增 MySQL/PostgreSQL `V7` migration；同步 `basic-schema.sql`

改动：

- 将 `fileId/chunkIndex/totalChunks/status` 的数字解析放入 `Mono.defer` / 参数校验链，非法值统一返回 `PARAM_INVALID`，不让异常在响应式链外抛出。
- 初始化时校验 chunkSize、totalChunks、fileSize 的上下限；上传分片在订阅时校验单片大小不超过初始化的 chunkSize，避免无限制 body 读入。
- merge 时严格校验请求中的 `fileName/contentType/md5` 与初始化记录/实际数据的关系；计算或流式校验分片 MD5 与最终文件 MD5，不再只保存而不验证；不匹配返回业务错误并清理临时对象/元数据。
- 将 `find-then-store-then-save` 改为数据库唯一约束 + 幂等写入；对重复 `(file_id, chunk_index)` 做明确的重复上传处理，避免并发留下多个对象和记录。
- 保持现有对象存储调度器与阻塞 IO 隔离，避免在 WebFlux handler 中引入 `.block()`。
- 增加非法数字参数、超单片、MD5 不匹配、重复分片、merge 失败清理、并发重复上传测试。

#### 2. 文件分享列表端点

修改：

- `apex-file/src/main/java/.../FileShareRepository.java`
- `.../FileShareRepositoryImpl.java`、Mapper/PO 查询
- `.../FileShareService.java`
- `apex-file-service/.../FileShareHandler.java`、`FileShareRouter.java`
- 新增 `FileShareItem` / `FileShareListQuery` DTO
- 前端 `src/api/file-share.ts` 与 `src/views/data/file-share/index.vue`

新增：

- `GET /api/v2/files/{fileId}/shares?page&size&status?`
- 只允许已认证用户查询自己有权访问的文件；查询同时绑定 `tenantId + fileId + creator/owner`，不能只按 fileId 查询。
- 返回 shareId/fileId/status/expireAt/createTime 等元数据，绝不返回 token/tokenHash。
- 使用数据库分页，超页返回空列表，不复用当前内存分页的 `subList` 越界模式。
- 增加跨租户、非文件所有者、过期分享、分页边界测试；前端将“创建后手动保存 shareId”升级为真实分享列表。

### Phase 2：修复 Keycloak 管理链路

修改：

- `apex-system/.../KeycloakUserSyncService.java`
- `TenantContext` 桥接点（JWT authentication filter / Handler 边界）
- `KeycloakAdminHandler.java`、`KeycloakRouterConfig.java`
- 新增 status/sync result DTO
- system migration（Keycloak 权限码与菜单/按钮权限）
- 相关 Handler/Service 集成测试

改动：

- 在认证过滤器到业务 Mono 的边界正确写入 `TenantContext`，保证 `TenantGuard` 能读取可信 JWT tenant；不依赖客户端 `X-Tenant-Id`。
- 单用户同步先按 tenant + `keycloak_sub` 查本地用户，明确“已存在则更新/跳过”的策略，避免重复建档唯一键冲突。
- 全量同步改为有限并发、汇总 `requested/synced/skipped/failed/errors`，失败不能吞掉后返回假成功。
- status 不再硬编码 `connected`；通过可隔离的 status/health port 调用 Keycloak Admin API，返回 enabled/status/error/checkedAt，并使用 `BlockingIoSchedulers.remote()` 隔离同步客户端调用。
- 为 status、全量同步、单用户同步分别增加 `@RequirePermission`，登记 `system:keycloak:status`、`system:keycloak:sync`、`system:keycloak:user:sync`，并补对应管理菜单/按钮权限。
- 增加 keycloak disabled、远端超时、重复同步、已存在用户、租户缺失、部分失败汇总测试。
- 修正 dev/Nacos 的 system upstream 默认端口，避免 `ROUTE_SYSTEM_URI=http://127.0.0.1:8080` 错指网关而不是 system-service 8082；补 gateway profile 配置测试。

### Phase 3：补通通知 SSE 的真实事件链路

修改：

- `apex-infrastructure-messaging/.../NotificationService.java`
- 新增明确的 `NotificationPublisher` / `NotificationMessage` DTO
- `MqProducerService` 使用点与业务事件生产方
- `NotificationBroadcastListener.java`
- `NotificationSseHandler.java`
- SSE/WebTestClient、MQ contract、跨实例隔离测试

改动：

- 定义稳定 payload：`id/messageId/tenantId/recipientId/content/type/createdAt`，校验 tenant、recipient、content 非空。
- 通过既有 `MqProducerService` 将业务通知发布到 `apex-notification-topic`；保留本地 multicast 与跨实例 listener，避免把本地 `publish` 误当 MQ producer。
- SSE 继续强制 Bearer + trusted tenant，不允许 query/header 覆盖租户；明确 event 名、data JSON、id/retry/heartbeat 格式。
- 对同租户同用户投递、跨租户拒绝、心跳 comment、真实 notification event、广播重复/丢失语义增加测试。
- 若当前业务没有自然通知来源，不伪造业务事件；先提供明确 publisher 接口并接入已有业务提交/消息完成事件，未接入业务在文档中说明。

### Phase 4：收敛认证中心会话/角色/权限安全边界

修改：

- `apex-auth-service/.../interfaces/handler/{SessionHandler,RoleHandler,PermissionHandler,AuthConfigHandler}.java`
- `.../interfaces/router` DTO/路径契约
- `AuthCenterConfig.java`、TenantContext 读取链
- auth-service integration/security tests
- 前端暂不切换到新 `/auth/v1/roles|permissions|sessions`，仅在契约稳定后增加适配层

改动：

- 对 session GET/online/statistics/detail、role/permission list/detail/resource/query 增加明确 admin/resource permission 门禁，不能只依赖认证状态。
- 统一 session ID 语义：不要让同一 `/{sessionId}` 在 GET 解析 Long、DELETE 却接受字符串 key；推荐拆分路径或统一为稳定 session key，并同步 OpenAPI/DTO/测试。
- AuthConfig 的 tenantId 必须来自可信认证主体/TenantContext；如果管理员需要跨租户操作，明确采用受控平台权限与审计字段，不直接信任 query tenantId。
- 保留 system 兼容 API 供现有前端使用；不要在后端安全门禁未补齐前把前端切到 auth-service 管理 API。补 gateway→auth-service contract test、普通用户 403、租户伪造 403 测试。

### Phase 5：前端同步与文档

- `src/api/file-share.ts` 增加安全分享列表接口，页面展示/撤销元数据。
- SSE 前端仍使用现有 fetch/WS 设计边界；只有后端 payload contract 固定后才加事件类型解析，避免先绑定裸字符串。
- Keycloak 管理页仅在 status 真实可用、权限码和 DTO 稳定后接入；不再展示硬编码状态。
- 更新 `docs/api/README.md`、`docs/guides/auth-tenant-adaptation.md`、后端运维文档，明确端点、权限、租户来源、payload 和 dev/prod upstream。

## Scope boundary

本计划不把上一轮暂缓项直接“接上”而掩盖后端缺陷；先修后端安全/一致性/事件链路，再同步前端。认证中心管理 API 在权限门禁、tenant 绑定和 session ID 语义修复前保持现有 system 兼容接口，不做危险切换。
